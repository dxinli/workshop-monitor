## 1. 用途与范围

本手册回答一个问题：**部署完之后，怎么证明每一段链路在工作，并且看得见它在工作。**

适用时机：

- 新环境首次部署完成后、移交或演示前
- 更换机器、重建容器栈、重新灌种后
- 点表 / 阈值 / 主题等配置变更后的复验
- 现场故障恢复后的分段定位

验证分三层，**按顺序做，不跳层**：

| 阶段 | 内容 | 不通过时 |
|---|---|---|
| 阶段 0 部署前置 | 工具、容器、配置投影、时序结构、读视图连通 | 不进链路验证，先修部署 |
| 阶段 1 独立链路 K1~K8 | 八条链路各自注入、各自观测、各自判读 | 只修该链路，不被其他链路的噪声带偏 |
| 阶段 2 完整链路 | 端到端生产路径、断网补传、告警触达、离线、配置生效、持续试运行 | 按分段定位法定位，回到阶段 1 对应链路复测 |

链路编号 K1~K8 与数据流编号 F1~F7 引自 [架构分析文档](11-架构分析文档.md) §3；
指标编号 MV-01~10 与用例编号 AC-01~20 引自 [验收标准](09-验收标准.md) 与 [测试用例](08-测试用例.md)。

**验证纪律**

1. 每条链路留证据：命令输出、SQL 结果、报文截取、截图，落到 `docs/evidence/<场景>/`。
2. 时间轴一律用 **采集时间 collectTime**；接收时间只用于时延排查，不做业务排序。
3. 失败路径要看质量码，不看数值——采集失败给空值 + 真实质量码，任何 0 值或沿用旧值都是缺陷，记下再继续。
4. 期望值以本手册与 `docs/08`、`docs/09` 的字面量为准，不以「上次跑出来的数」为准。

## 2. 观测面总览（先读这一章）

链路结果可观测，靠六个观测面。**每验证一条链路，至少在一个观测面上看到结果才算验过**；
能在两个观测面上交叉印证的（例如报文 + 库行），优先交叉。

| # | 观测面 | 位置 | 看什么 | 主要覆盖 |
|---|---|---|---|---|
| O1 | 健康检查 | `edge-agent` 9101~9105、`proto-adapter` 9200 的 `/healthz` | 分项状态、积压、活动告警对账 | K1 K2 K3 K5 |
| O2 | 结构化日志 | 两个自研进程的 stdout | `ts/level/svc/inst/msg`，带 `esn`/`pointId`/`seq` | 全部 |
| O3 | MQTT 报文 | Broker 1883，`mosquitto_sub` | 报文头 8 字段、`backfill`、主题命名 | K2 K3 |
| O4 | 库表与视图 | TimescaleDB 5432，`monitor.*` | 幂等、历史、实时值、告警、通知、状态 | K4 K5 K6 K8 |
| O5 | Grafana 读视图 | 3000，8 个只读面板 | 呈现结果与刷新粒度 | K8、完整链路 |
| O6 | 通知留痕 | Node-RED 日志、`notify_log`、wecom-mock 记录 | 投递成败、重试、卡片字段 | K5 |

### 2.1 观测命令速查

下文统一下述别名，先在仓库根目录执行一次：

```bash
DC="docker compose -f deploy/docker-compose.yml --env-file deploy/versions.env --env-file .env"

# 库查询：口令不落命令行，容器内从环境取（与 preflight.sh 同一手法）
SQL() { $DC exec -T timescaledb sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -tAc "$1"' _ "$1"; }

# 口令载入宿主机环境（订阅与发布要用）
set -a; . ./.env; set +a
```

**O1 健康检查**

```bash
curl -s http://127.0.0.1:9101/healthz            # ESN-ZX-0001，其余终端 9102~9105
curl -s http://127.0.0.1:9200/healthz            # proto-adapter
```

- `edge-agent` 返回 `status` + `checks.{config,serial,mqtt,cache}`；
  `cache` 含 `depth`/`bytes`/`dropCount`——**断网积压就看这三个数**。
- `proto-adapter` 返回 `checks.{mqtt,ingest,evaluate}`；`evaluate` 含
  `queueDepth`/`dropCount`/`activeAlarmCount`/`debounceKeys`，
  并把内存里的活动告警数与库里的 `activeAlarmCountInDB` **对账**（`reason` 非空即不一致）。
- HTTP 200 = 就绪或降级，503 = 不可用。降级也返回 200，**要看 `status` 字段，不能只看 HTTP 码**。

**O3 MQTT 报文**

主题模板的唯一来源是 `config/topics.json`，两套方案同形、仅前缀不同（`grid` 用 `/edge/`、
`internal` 用 `/workshop/`），下文以 `grid` 为例：

```bash
# 旁听全部上行。-R 必带：状态主题是 Retain 的，不加会把历史状态当新消息看
$DC exec -T -e PW="$MQTT_WORKSHOP_ADAPTER_PASSWORD" mosquitto \
  sh -c 'mosquitto_sub -h 127.0.0.1 -u workshop_adapter -P "$PW" -t "/edge/#" -R -v'

# 只看一台终端的数据报文
$DC exec -T -e PW="$MQTT_WORKSHOP_ADAPTER_PASSWORD" mosquitto \
  sh -c 'mosquitto_sub -h 127.0.0.1 -u workshop_adapter -P "$PW" -t "/edge/ESN-ZX-0001/data/up" -R -v'
```

> 涉及 Broker 重启 / 停机的观测，**不要用 `docker exec` 起订阅端**（会随容器一起被杀）。
> 用独立容器挂宿主机网络：
> `docker run --rm -i --network host eclipse-mosquitto:<版本> mosquitto_sub -h 127.0.0.1 ...`
> （版本号取 `deploy/versions.env` 的 `MOSQUITTO_VERSION`。）

**O4 库查询常用口**

```bash
SQL "SELECT count(*) FROM monitor.measurement WHERE collect_time > now() - interval '1 min'"
SQL "SELECT terminal_id, status, last_data_time, offline_reason FROM monitor.terminal_state ORDER BY 1"
SQL "SELECT alarm_id, dedupe_key, level, status, occur_time, recover_time FROM monitor.alarm ORDER BY occur_time DESC LIMIT 5"
SQL "SELECT notify_id, alarm_id, status, retry_count, http_code FROM monitor.notify_log ORDER BY sent_time DESC LIMIT 5"
```

**O5 Grafana**：`http://localhost:3000`，匿名 Viewer，无登录表单。8 个面板见 §2.2。

**O6 通知留痕**：`wecom-mock` 在 8081（宿主机回环），记录库 `var/wecom-mock.db`（宿主机 venv 形态）
或 `wecom-data` 卷（容器形态）；投递日志在 `monitor.notify_log`。

## 3. 阶段 0：部署前置自检

链路验证之前，先确认「部署完能不能用」。任一项失败就停下修部署，不进阶段 1。

### 3.1 准备

```bash
cp .env.example .env          # 首次：填全部口令
make passwd                   # 按 .env 与 ACL 生成 Mosquitto 口令文件
make build                    # 构建二进制（含 config-tool）
make seed-sql && make seed    # 配置 → 02_seed.sql → 导入库
make up                       # 起 core 四容器
```

- `make up` 只起 `core` profile（timescaledb / mosquitto / node-red / grafana）。
  仿真件另起：`make sim-pty && make sim-up`、`make sim-wecom`（或 `docker compose --profile sim up -d wecom-mock`）。
- 采集应用不在 compose 里（终端与平台分别部署），起法见 §4.1。

### 3.2 自检命令与判据

```bash
make verify-config   # V-01~V-11 逐条验证，含「造坏配置看报错内容」
make preflight       # 12 项部署后自检
make preflight HEALTH_URLS=http://127.0.0.1:9101/healthz,http://127.0.0.1:9200/healthz
```

`make preflight` 判据（12 项全 ok，输出「自检通过」）：

| 项 | 通过读数 | 失败含义 |
|---:|---|---|
| 1~5 | 工具、`versions.env`、compose 文件、`.env`、`config/terminals` 在 | 部署前置缺失 |
| 6~9 | 四个容器 running | 对应容器没起来 |
| 10 | 配置域投影 `5/50/140/95` | `make seed` 没跑或跑在旧配置上 |
| 11 | 超表 / 分钟聚合 / 明细 7 天 / 聚合 30 天 = `1/1/1/1` | 建表脚本没跑完整 |
| 12 | Grafana `/api/health` 报 `database: ok` | 读视图连不上库 |

附加的 `HEALTH_URLS` 不计入 12 项，但**阶段 1 开始前应当全绿**——两个自研服务的
`/healthz` 是后面所有链路观测的基线。

## 4. 阶段 1：独立链路验证 K1~K8

每条链路一节，结构固定：**前置 → 注入 / 操作 → 观测点 → 通过判据 → 失败排查**。
链路间的依赖只有一条：K1~K3 需要仿真链路就绪（`make sim-pty && make sim-up`）；
K5/K8 需要 core 栈与库已 seed。其余互不阻塞，可单独重测。

### 4.1 K1 采集换算链路（F1 前段）

**边界**：边缘进程内闭环（从站寄存器 → 帧 → 工程值 → 批次），不依赖网络与平台。
失败点也进批次：空值 + 真实质量码，**不得沿用旧值或填 0**。

**前置**：`make sim-pty` 已建 10 对虚拟串口（`.pty/ports.json` 模拟器端、
`.pty/agent-ports.json` 采集端）；`make sim-up` 已起从站模拟器。

**注入 / 操作**（以 ESN-ZX-0001 为例，其余终端换配置与健康口）：

```bash
set -a; . ./.env; set +a
HEALTH_ADDR=127.0.0.1:9101 go run ./cmd/edge-agent \
  -config config/terminals/ESN-ZX-0001.json -ports .pty/agent-ports.json
```

注入手段三选一，按要验的点选：

| 要验 | 注入 | 期望 |
|---|---|---|
| 地址 / 换算正确 | 模拟器写全局唯一哨兵原始值，逐点读回 | 与点表一一对应（AC-02） |
| 缩放 / 字节序 / 符号扩展 | 注入 int16/uint16/int32/uint32 边界与负值 | 工程值按 `scale`/`offset`/`byteOrder` 正确（AC-03） |
| 失败路径质量码 | 模拟器注入超时 / CRC 错 / 超量程 | 空值 + 真实质量码，量程外保留数值只改质量码 |

**观测点**：

```bash
curl -s http://127.0.0.1:9101/healthz    # checks.serial：各总线状态；checks.config：configVersion
```

- O1：`checks.serial` 按总线给状态；`status` 总体 `up`。
- O2：日志按周期聚合，**不逐点打印成功日志**；采集失败与重试（Modbus 读超时 2 次、CRC 1 次）有上下文行。
- O3（若同时起 MQTT）：`header.collectTime` = 本批读帧解析完成时刻，批内一致。

**通过判据**：

1. 连续 30 个采集周期间隔稳定在 5000 ms 附近（AC-01 / MV-09），无测点漏采。
2. 哨兵核对 140 行全部一致（AC-02 证据形态 `point_check.csv`）。
3. 失败路径全部是空值 + 真实质量码，无 0 值、无旧值。

**失败排查**：`serial` 不 up → 查 `.pty/agent-ports.json` 与模拟器 `.pty/ports.json` 是否同一对；
周期不稳 → 查模拟器侧日志与串口超时参数（`bus.timeout_ms`/`retry_count`）；
换算错 → 对点表 `dataType`/`byteOrder`/`scale`/`offset`，换算逻辑只在 `internal/agent/codec.go`。

### 4.2 K2 上行发布链路（F1 中段）

**边界**：仅依赖 MQTT 连接，序号自持。出队凭据是 **PUBACK**，不是「已发出」；
序号在进缓存前就已分配，**终端内单调递增、重启不归零**。

**前置**：K1 在跑；Broker 已起；`.env` 里有 `MQTT_ESN_ZX_0001_PASSWORD` 等口令。

**操作**：不做额外注入，正常上报即可；要做断连分支时看 K3。

**观测点**：

```bash
# O3：读报文头
$DC exec -T -e PW="$MQTT_WORKSHOP_ADAPTER_PASSWORD" mosquitto \
  sh -c 'mosquitto_sub -h 127.0.0.1 -u workshop_adapter -P "$PW" -t "/edge/ESN-ZX-0001/data/up" -R -v'
```

报文头必查字段（契约见 [接口规范](04-接口规范.md) §4.3）：

| 字段 | 期望 |
|---|---|
| `esn` | 与主题中 `{esn}` 完全一致，不一致平台判 `IDENTITY_MISMATCH` |
| `seq` | 严格递增，跳号允许、**重号禁止**；重启后续接不归零 |
| `msgId` | `{esn}-{seq:08d}` |
| `collectTime` / `sendTime` | 毫秒；正常上报两者差 ≈ 一次采集耗时（MV-01 口径） |
| `backfill` | 正常上报 `false` |

- O1：`checks.mqtt.connected = true`，`lastSuccess` 刷新。
- O4 交叉：`message_log` 按 `(terminal_id, seq)` 落行，`parse_status = OK`。

**通过判据**：连续 30 条报文 `seq` 严格递增无重号（AC-01/AC-13 序号判据）；
`esn` 与主题一致；重启 agent 后 `seq` 从队列最大序号续接。

**失败排查**：发不出去 → `checks.mqtt` 与 Broker 日志（账号口令是否与 `gen-passwd.sh` 同步）；
被 ACL 拒 → `make verify-broker`（注意：3.1.1 下越权发布退出码是 0，要看 Broker 日志或用 `-V mqttv5` 验证）。

### 4.3 K3 缓存补传链路（F2）

**边界**：独立协程 + 独立持久队列。断网时采集不中断、数据落盘；恢复后按 `seq` 升序补传，
**保留原 `collectTime`，置 `backfill=true`，`sendTime` 更新为补传时刻**。
三上限（7 天 / 30 万条 / 512 MB）任一先到即 FIFO 裁剪，不静默。

**前置**：K2 在跑；`-cache` 指向真实文件（默认 `var/cache.db`）；Broker 可停可起。

**注入 / 操作**：

```bash
$DC stop mosquitto        # 断上行，采集应不受影响
# ……持续 ≥ 5 个采集周期……
$DC start mosquitto       # 恢复，触发补传
```

**观测点**：

| 时刻 | 面 | 期望 |
|---|---|---|
| 断网中 | O1 `checks.cache` | `depth`/`bytes` 单调增长；`dropCount` 仅在裁剪后非 0 |
| 断网中 | O1 / O2 | 采集周期间隔不变（补传不拖采集，AC-16） |
| 断网中 | O3（独立订阅端，见 §2.1 注） | 无该终端新报文 |
| 恢复后 | O3 | `backfill=true` 的报文 `seq` 严格正序、`collectTime` 为断网期间的旧值 |
| 恢复后 | O1 `checks.cache` | `depth` 回落（AC 判据「队列深度回落」） |
| 恢复后 | O4 | `measurement.backfill = true` 的行只进历史，**不覆盖实时值** |

裁剪留痕（可压低 `CACHE_MAX_*` 制造，验完恢复）：每满 1000 条一个 `CACHE_DROPPED` 事件；
任一维度达 80% 一个 `CACHE_WARNING`，同级不重复。

**通过判据**（AC-09 ~ AC-13、AC-16）：

1. 断网期间采集周期不受影响，队列深度单调增。
2. 补传报文 `seq` 严格正序、`collectTime` 保留、`backfill=true`。
3. 每轮补传 ≤ 500 条、批间隔 ≥ 50 ms（`BACKFILL_BATCH`/`BACKFILL_INTERVAL_MS`）。
4. 补传后 `realtime_value.collect_time` **不回退**（只被更晚 `collectTime` 覆盖）。
5. 杀进程重启后队列条数不丢；收到 PUBACK 才出队。

**失败排查**：`depth` 不涨 → `-cache` 是不是空串（空串 = 不落盘）；
不补传 → `checks.mqtt` 是否已连通、`BACKFILL_*` 参数；
实时值回退 → 这是缺陷（条件写必须在 SQL `WHERE` 里），留证据报缺陷，不改判据。

### 4.4 K4 接收落库链路（F1 后段）

**边界**：平台进程内闭环，幂等自持。**幂等判定在写任何业务表之前**；
重复报文判 `DUPLICATE` 不写业务表；实时值只被更晚 `collectTime` 覆盖。

**前置**：`proto-adapter` 在跑（`go run ./cmd/proto-adapter -config config/adapter.json`，
健康口 9200）；库已 seed。

**注入 / 操作**：正常上报即可；验幂等需重复投递一条报文：

```bash
# 从 O3 抓一条完整报文保存为 payload.json 后重发一次
$DC exec -T -e PW="$MQTT_ESN_ZX_0001_PASSWORD" mosquitto \
  sh -c 'mosquitto_pub -h 127.0.0.1 -u ESN-ZX-0001 -P "$PW" -t "/edge/ESN-ZX-0001/data/up" -f /tmp/payload.json'
```

（`payload.json` 需先 `docker cp` 进容器，或改用宿主机侧 `mosquitto_pub`。）

**观测点**：

```bash
SQL "SELECT parse_status, count(*) FROM monitor.message_log GROUP BY 1 ORDER BY 1"
SQL "SELECT terminal_id, seq, parse_status, fail_reason FROM monitor.message_log ORDER BY receive_time DESC LIMIT 5"
SQL "SELECT count(*), max(collect_time) FROM monitor.measurement WHERE collect_time > now() - interval '5 min'"
SQL "SELECT point_id, value, quality, collect_time, seq FROM monitor.v_realtime WHERE terminal_id='ESN-ZX-0001' ORDER BY point_id LIMIT 5"
SQL "SELECT receive_time, parse_status, fail_reason FROM monitor.v_raw_recent LIMIT 5"
```

| 观测 | 期望 |
|---|---|
| `message_log` | 首次 `OK`，重发同 `seq` 为 `DUPLICATE`；主键 `(terminal_id, seq)` |
| `raw_message` / `v_raw_recent` | 原文不裁剪，解析失败有 `fail_reason` |
| `measurement` | 每采集周期按测点增长；质量非 0 的行 `value IS NULL` |
| `realtime_value` | 恒定 140 行；`collect_time` 只进不退（AC-14） |
| 补传行 | 只进 `measurement`，不推进 `realtime_value` |

**通过判据**（AC-12、AC-14、AC-17）：

1. 同 `seq` 重复投递：首次 `OK`、重复 `DUPLICATE`、业务表不产生重复行。
2. 先写较新 `collectTime` 再写较旧的，实时值不被旧值覆盖。
3. 幂等判定失败时不写任何业务表。

**失败排查**：`PARSE_ERROR` → 看 `fail_reason` 与 `v_raw_recent` 原文；
`IDENTITY_MISMATCH` → 报文 `header.esn` 与主题不一致；
数据不进库 → 9200 的 `checks.mqtt`/`checks.ingest`，以及 Broker 侧 adapter 订阅是否在线（持久会话）。

### 4.5 K5 告警判定与触达链路（F3）

**边界**：与入库经有界 channel 解耦。判定逻辑只在 `internal/adapter/evaluate`：
质量非 `GOOD` 在入口即返回；模拟量去抖连续 N 次触发 / N 次恢复；开关量不去抖、当次即动；
未恢复不重复拉响（去重键 `terminalId|pointId|alarmType`）；补传数据只记历史越限，**不发通知**。

**前置**：K4 在跑；阈值已 seed（95 条）；Node-RED 已起（`make up`）；
通知接收端 `make sim-wecom` 或 `docker compose --profile sim up -d wecom-mock`。

**注入 / 操作**（工况预设，`config/scenes.json`，模拟器 `127.0.0.1:8080`）：

```bash
curl -s -X POST http://127.0.0.1:8080/api/v1/scene/alarm    # 越限工况：高高限/高限/低限
curl -s -X POST http://127.0.0.1:8080/api/v1/scene/safety   # 安全工况：门磁/急停/光幕置 1
curl -s -X POST http://127.0.0.1:8080/api/v1/scene/normal   # 复位：回阈值内
```

分项注入：

| 要验 | 操作 | 期望 |
|---|---|---|
| 去抖 N 次（AC-04） | 单点越限连续采 N 次 | 第 N 次才拉响；单次波动不告警 |
| 恢复 N 次（AC-05） | 越限后回阈值内 1 次再越限，循环 N-1 次，最后连续 N 次不越限 | 中途不恢复；**首次未命中即恢复是缺陷** |
| 开关量不去抖（AC-06） | `door`/`estop` 置 1 → 采 1 次 → 置 0 | 当次告警、当次恢复 |
| 高高限闭合高限（AC-07） | 先越高限，再越高高限 | 同测点 `HIGH_LIMIT` 活动告警被闭合，去重键下只一条 ACTIVE |
| 质量门槛（AC-08） | 造质量非 0 的越限读数 | 判定入口即返回，不告警、不推进去抖计数 |

**观测点**：

```bash
SQL "SELECT alarm_id, dedupe_key, alarm_type, level, status, trigger_value, occur_time, recover_time FROM monitor.alarm ORDER BY occur_time DESC LIMIT 10"
SQL "SELECT count(*) FROM monitor.alarm WHERE status='ACTIVE'"
SQL "SELECT notify_id, alarm_id, status, retry_count, http_code, fail_reason FROM monitor.notify_log ORDER BY sent_time DESC LIMIT 10"
```

- O4：`alarm.occur_time` **就是采集时间**；`status` 轨迹 `ACTIVE → RECOVERED`（确认另记 `alarm_ack`，不改 `alarm.status`）。
- O4 对账：`level >= 2` 的告警必须 100% 有 `notify_log` 行（MV-08，成功失败都留痕，不静默）；
  `level = 1` 只入库不发通知。
- O6：卡片含车间、终端、设备、测点、级别、触发值、发生时间、告警原因（AC-18）；
  失败重试 4 次（立即 / 1s / 5s / 15s），末端 `FAILED` 带 `fail_reason`。
- 通知失败**不回滚告警、不阻塞落库**。

**通过判据**（AC-04 ~ AC-08、AC-18、MV-08）：上表五个分项注入全部符合期望；
`make verify-notify` 通过（卡片字段、级别分流、重试与投递日志）。

**失败排查**：告警不出 → 9200 的 `checks.evaluate`（`debounceKeys` 是否在计数）、阈值是否 `enabled`、质量是否 `GOOD`；
通知不出 → Node-RED 日志、`WECOM_ENABLED`/`WECOM_WEBHOOK_URL`、wecom-mock 是否在 8081；
`notify_log` 无行但告警有 → 只有 level 1 或 `backfill=true` 的告警才允许这样。

### 4.6 K6 终端状态合成链路（F4）

**边界**：三源输入独立于测点值判定，**缺一都会误判**：

| 源 | 语义 | 优先级 |
|---|---|---|
| STATUS 报文 / LWT 遗嘱 | 显式离线 | 最高 |
| DATA 非补传 | 推进 `lastData`、置在线 | — |
| 巡检（sweepLoop） | 超 3 个周期无数据判离线 | 兜底 |

补传数据**不推进** `lastData`。设备离线独立于终端离线：连续 5 次采集失败记设备离线，
分别告警、分别展示。

**注入 / 操作**：

| 要验 | 操作 | 期望 |
|---|---|---|
| 显式离线 | kill agent 进程（触发 LWT） | `terminal_state` 转 `OFFLINE`，`offline_reason` 为意外断开 |
| 进程假死 | 挂起进程但不杀连接 | 数据超时兜底判离线（只看 LWT 会漏） |
| 补传误判 | 断网积压后恢复补传 | 补传期间与补传报文**不**把终端判回在线 |
| 设备离线 | 模拟器停一台从站 | `device_event` 记设备离线，终端状态不受影响 |

**观测点**：

```bash
SQL "SELECT terminal_id, status, last_data_time, last_seen_time, offline_reason FROM monitor.terminal_state ORDER BY 1"
SQL "SELECT terminal_id, event_type, event_time, reason FROM monitor.device_event ORDER BY event_time DESC LIMIT 10"
```

O5 车间总览面板同屏看在线状态与最后上报；O3 可看状态主题（Retain，新订阅者立即拿到最后状态）。

**通过判据**：三种注入各自只产生对应的状态变化；恢复上报后转 `ONLINE`；
补传不推进 `lastData`；终端离线与设备离线是两条独立记录。

### 4.7 K7 配置装载链路（F6）

**边界**：配置文件是唯一权威源，数据库是投影；与运行期数据流正交。
生效边界（[deploy 规则](../.claude/rules/deploy-config.md)）：

| 变更 | 生效 | 重启 |
|---|---|---|
| 阈值数值 / 级别 | 60 秒内热载、原子替换 | 否 |
| 工况预设 | 下次场景切换 | 否 |
| 点表地址 / 数量 / 字节序 | 重启对应终端 | 是 |
| 串口参数 | 重启 | 是 |
| 主题命名方案 | 重启 agent 与 adapter | 是 |

**操作与观测**：

```bash
make verify-config     # V-01~V-11，逐条造坏配置验证报错含具体字段与原始值
make seed-sql && make seed
make preflight         # 第 10 项：投影 5/50/140/95
SQL "SELECT count(*) FROM monitor.terminal"     # 5
SQL "SELECT count(*) FROM monitor.point"        # 140
SQL "SELECT count(*) FROM monitor.threshold"    # 95
```

阈值热载验证（AC-19）：改 `config/thresholds.json` 一个数值 → 60 秒内不重启 →
按新阈值触发 / 不触发；`git diff` 证明只改了配置。

**通过判据**：

1. `make verify-config` 全过，坏配置报错**含具体字段与原始值**，不只说「配置错误」。
2. 投影计数 `5/50/140/95`；`02_seed.sql` 与 `config/` 同步（`make config-check`）。
3. 阈值改动 60 秒生效；点表改动必须重启才生效（**不做热加载**，热加载半个周期错值）。

### 4.8 K8 展示与确认链路（F7）

**边界**：读写分离出口。Grafana 全程只读（Viewer，写操作 403）；写集中在 Dashboard 一处；
确认**只写 `alarm_ack`，不改 `alarm.status`**（状态机先恢复后确认）。

**操作与观测**：

```bash
make verify-read-view   # 8 面板可读、只读、30 天走聚合（EXPLAIN 命中 measurement_1m）
make verify-ack         # 活动告警清单、确认写 alarm_ack、场景切换、写视图权限
```

人工核对：

1. 8 个面板（§2.3）全部有数据或合理空态；「最近一次正常值」同屏标注**采集时间与质量**；
   校验错误、超量程值视觉可区分。
2. 30 天趋势查询走 `measurement_1m`，不扫明细（MV-07，证据形态 `plan-30d.txt`）。
3. Dashboard（`/dashboard/ops`）确认一条告警 → 库里 `alarm_ack` 多一行，
   `alarm.status` **不变**；`acked_by`/`acked_time` 正确。

**通过判据**（AC-15 库权限部分、MV-07）：`make verify-read-view` 与 `make verify-ack` 全过；
Grafana 只读账号写操作被拒；确认写对表、不改状态机。

## 5. 阶段 2：完整链路验证

独立链路全过之后，再跑端到端。完整链路验证的是**段与段之间的衔接**：
同一时刻、同一条数据，在各段的读数互相咬合。

### 5.1 E2E-1 正常生产链路（F1：寄存器 → 界面）

**路径**：从站寄存器 →（K1）→ 报文 →（K2）→ Broker →（K4）→ 库 →（K8）→ Grafana；
同时经 channel 进（K5）判定段。

**操作**：全链路起齐（core + sim + 5 台 agent + adapter），场景 `normal`，跑 10 分钟。

**观测与判据**：

1. **同一 `seq` 五处咬合**（任取一条非补传报文）：
   - O3 报文头的 `seq`/`collectTime`
   - `message_log` 同 `(terminal_id, seq)` 行
   - `measurement` 该批 28 行（每终端每周期 28 测点）同 `collect_time`
   - `realtime_value` 对应测点 `seq` 与 `collect_time`
   - O5 实时监视面板显示值与质量
2. **时延实测**（MV-01/02/04，采样 100 条取 P95）：

```sql
-- MV-01 采集→上报（目标 ≤ 2000 ms）
SELECT percentile_cont(0.95) WITHIN GROUP (
  ORDER BY extract(epoch FROM (send_time - collect_time)) * 1000)
FROM monitor.measurement
WHERE NOT backfill AND send_time > now() - interval '10 min';

-- MV-02 上报→入库（目标 ≤ 3000 ms）
SELECT percentile_cont(0.95) WITHIN GROUP (
  ORDER BY extract(epoch FROM (receive_time - send_time)) * 1000)
FROM monitor.measurement
WHERE NOT backfill AND receive_time > now() - interval '10 min';
```

MV-04 端到端（目标 ≤ 采集周期 + 10 秒，5 秒周期即 ≤ 15 秒）在界面量：
记面板上某测点的 `collectTime`，看墙钟何时呈现；重复 10 次取最差值。
近似口径：`MV-01 + MV-02 + 面板刷新 ≤ 5 秒`。

3. **采集性能**（MV-09）：连续 30 个周期每周期 140 测点、间隔 5000 ms ± 抖动。
4. **呈现**（MV-03）：面板刷新间隔配置为 5s，连续两次取值观测间隔 ≤ 5 秒。

### 5.2 E2E-2 断网补传链路（F2：积压 → 恢复 → 落位）

**操作**：`$DC stop mosquitto` → 跑 ≥ 5 个周期 → `kill` 一台 agent 再重启 → `$DC start mosquitto`。

**观测与判据**：

1. 断网期间 O1 `cache.depth` 单调增，采集周期不变（K3 判据 1）。
2. 进程重启后队列条数不丢（AC-11）。
3. 恢复后 O3 收到 `backfill=true` 报文：`seq` 正序、`collectTime` 为旧值、`sendTime` 为补传时刻（AC-13）。
4. 落位正确：补传行进 `measurement`（`backfill=true`），`realtime_value.collect_time` 不回退（AC-12）。
5. 幂等门兜住重发：`message_log` 无重号，历史无重复行（AC-17）。

### 5.3 E2E-3 告警触达链路（F3：越限 → 告警 → 通知 → 确认）

**操作**：`POST /api/v1/scene/alarm` → 等去抖 N 个周期 → `scene/normal` 恢复 → Dashboard 确认一条。

**观测与判据**：

1. `alarm` 行的 `occur_time` 与越限采集批次的 `collect_time` 对齐（业务时间轴一致）。
2. `level>=2` 的告警 100% 进 `notify_log`（MV-08）；O6 卡片字段八项齐全（AC-18）。
3. 恢复后 `status=RECOVERED`、`recover_time` 为恢复时的采集时间；确认后多一条 `alarm_ack`，
   `alarm.status` 不被改写。
4. O5 告警中心与库里同屏对得上；故障注入（停 wecom-mock）→ 重试 4 次后 `FAILED` 留痕，
   告警本身不受影响。

### 5.4 E2E-4 离线链路（F4：断连 → 状态 → 展示）

**操作**：kill 一台 agent → 恢复 → 再做一次「假死」（挂起不杀）。

**观测与判据**：`terminal_state`/`device_event` 轨迹符合 K6 三源规则；O5 车间总览同步；
恢复上报后回 `ONLINE`；全程无误报（补传不推进 `lastData`）。

### 5.5 E2E-5 配置变更生效（F6 / AC-19）

**操作**：只改配置、不改代码（`git diff` 证明），五类变更各做一次：
阈值数值、工况预设、点表地址、串口参数、主题 / 通知通道地址。

**观测与判据**：按 §4.7 生效边界表各自生效；切换通知通道只改 `WECOM_WEBHOOK_URL`；
改动前后行为差异可在对应观测面上看到。

### 5.6 E2E-6 持续试运行（稳定性）

**操作**：全链路连续运行 ≥ 2 小时（形态参考 `scripts/accept-016.py`：后台跑批、自动采证）。

**观测与判据**：

1. 采集周期间隔序列稳定，无漏采、无重复上报。
2. 队列深度回落并保持低位（缓存不积）。
3. 分钟聚合持续出数（`measurement_1m`），30 天查询走聚合（MV-07）。
4. 保留策略真实生效（可造 8 天前数据跑策略验证清理，MV-06）。
5. 磁盘占用在 50 GB 预算内；镜像总体积 ≤ 3 GB、单机 4 核 / 8 GB 可跑（MV-10，`docker system df`）。
6. 期间两个 `/healthz` 无降级转不可用。

## 6. 结果记录与判读

### 6.1 记录表模板

每条链路一行，证据另存文件：

| 链路 | 场景 | 操作摘要 | 观测面 | 读数（粘贴原文） | 期望 | 结论 |
|---|---|---|---|---|---|---|
| K1 | 例：边界值换算 | int16 注入 -32768 | O1/O3 | （读数） | 缩放正确 | 通过 / 不通过 / 阻塞 |

完整链路另记时延表（MV-01/02/04 各一列 P95）与稳定性观测（周期间隔、队列深度序列）。
证据目录建议 `docs/evidence/verify-<场景>/`，形态沿用既有验收证据
（`acceptance.json` + `README.md` + 报文 / SQL 截取）。

### 6.2 判读原则

- 结论分三档，口径同 [验收标准](09-验收标准.md) §二：**通过 / 有条件通过 / 不通过**，
  不合成一句「完成」——Standards（是否符合规范）与 Spec（是否只做了要求的事）两轴分别报。
- 期望值以文档字面量为准。实测与文档冲突时**先停车确认哪边错**，改文档再改代码，
  不按「能跑的方式」放行。
- 缺陷分级沿用 A / B / C：A 阻断演示或数据不可信（必须修复复验），B 功能缺失或口径错误
  （修复或明确降级），C 体验或文档问题（记录不要求本次修复）。

### 6.3 失败时的分段定位法

一段链路不通时，**由近及远**看观测面，找到第一处读数不对的段，就是故障段：

```text
O1 /healthz（进程活着吗、连着吗、积压吗）
 → O2 日志（这一段报了什么错）
   → O3 报文（数据出来了吗、字段对吗）
     → O4 库（进来了吗、进对表了吗）
       → O5 界面（查对了吗、呈现对吗）
         → O6 通知（发出去了吗、留痕了吗）
```

例：界面上没数据——先查 `v_realtime`（K4/K8）；库里有库里对，查面板时间范围与数据源（K8）；
库里没有，查 `message_log`（K4 解析）；`message_log` 没有，看 O3 报文（K2）；
报文没有，看 O1 `mqtt`/`cache`（K2/K3）与 `serial`（K1）。
