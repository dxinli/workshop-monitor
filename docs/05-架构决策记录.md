## ADR-01　分层而非微服务

**决策**：按 L0~L7 分层，同层内单进程，不引入服务注册、网关、独立消息总线。

**被否方案**：微服务拆分、K8s 编排。

**理由**：单机 4 核 / 8 GB 是硬约束，5 个终端的规模不需要弹性伸缩；微服务会把"中间件不超过 4 类"直接突破，
而这条约束是整个轻量化目标的前提。

**代价**：无水平扩展能力，数据库单点。**明确接受**——需求已排除高可用。

## ADR-02　Broker 选轻量代理（Mosquitto）

**决策**：Mosquitto 2.x，MQTT 3.1.1 + QoS 1 + 持久会话。

**被否方案与落选原因**：

| 候选 | 落选原因 |
|---|---|
| EMQX 5.x | 内存 500 MB+、镜像大；其规则引擎与自研适配层职责重叠，引入后产生"两处改协议"风险 |
| NanoMQ | 够轻，但 ACL 表达力弱、社区资料少，不利于交付后客户自行维护 |
| HiveMQ CE | 许可与扩展限制，且体积偏大 |

**代价**：ACL 为静态文件，改权限需重载。演示期可接受，正式项目建议换支持动态 ACL 的 Broker——可替换点已预留（仅 Topic 语义依赖）。

## ADR-03　时序与关系数据合并为一套库

**决策**：TimescaleDB（PostgreSQL 扩展），同一实例承载关系数据与时序数据。

**被否方案与落选原因**：

| 候选 | 落选原因 |
|---|---|
| TDengine | 压缩率更优、写入更强；但需**第二套数据库**，越过"中间件 ≤ 4 类"，且关系数据仍需 PG，运维与备份翻倍 |
| InfluxDB OSS | 关系数据仍需第二套库；2.x / 3.x 版本路线变动大，交付风险高 |
| QuestDB | 关系能力弱，配置域与告警域无处安放 |
| 纯 PostgreSQL（不装扩展） | 30 天聚合查询需自建分区与降采样任务，等于自研时序能力，违反"平台侧中间件一律复用开源" |

**收益**：一次备份、一套账号、一套 SQL 方言、一个连接池；连续聚合直接解决 30 天曲线。

## ADR-04　告警判定下沉到接入服务，编排层只负责触达

**决策**：阈值求值、去抖计数、状态机放在接入服务内部的独立模块；编排层只做"收到通知请求 → 投递 → 失败重试 → 记录"。

**被否方案**：把告警全流程放在可视化编排工具里（即本项目早期方案）。

| 被否原因 | 具体问题 |
|---|---|
| 去抖是**有状态时间窗口**，本质是业务逻辑 | 状态藏在流程上下文中，**无法单元测试、无法 code review diff**。产品最核心的判定规则长这样，是不可接受的脆点 |
| 判定与触达绑定 | 编排层一挂，无告警产生；分离后编排层挂，告警照常判定入库，仅推送与确认不可用 |
| 阈值规则的可测性 | 用可视化 function 节点写的片段难以纳入 CI，回归靠人工点页面 |

**曾考虑的中间选项**：自研独立 alerter 服务承担判定。落选原因——会把自研服务数推到 3，
逼近上限（≤4），且与接入服务之间需再造一次内部序列化（幂等键、采集时间、质量码都要穿过这条边界）。
合并进接入服务并分模块（见 ADR-07），既守住服务数上限，又保留模块可测性。

**带来的结构性收益**：告警的**产生**与**触达**分离。

| 场景 | 原方案 | 本方案 |
|---|---|---|
| 编排层故障 | 无告警产生，判定逻辑全丢 | 告警照常判定入库，仅推送与确认不可用 |
| 数据入库 | 不受影响 | 不受影响 |

**代价**：接入服务职责变宽（协议转换 + 告警判定），内部必须严格分模块，否则变成一处臃肿逻辑。

**连带影响**：

1. 内部事件主题族取消，改为 HTTP 通知请求（少一跳、少一处序列化、免去内部事件 Schema 的维护成本）；
2. 编排层不再需要持久化上下文存储——去抖计数改由接入服务纯内存持有；
3. 编排层不再读写告警表的发生与恢复，仅写通知记录；告警确认仍由操作视图写。

## ADR-05　入库与判定之间用进程内异步队列

**决策**：入库成功后投递到有界队列，由单一消费者执行判定。

**被否方案一：同步调用。** 求值耗时直接计入入库耗时，拖累入库时延；求值异常污染入库错误率。

**被否方案二：经消息代理自转发。** 去抖是内存态计数，重放历史事件会让计数虚高，**制造误报**；误报比重判更难排查。

**理由**：入库失败会丢数据，判定失败只漏告警，两者严重性不同，不该串在一条同步链上。

**有界的意义**：队列有界天然形成背压——判定变慢时入库侧会在队列满时感知到，而不是无限堆积内存。
满时选择计数丢弃而非阻塞入库，因为"少一条告警"比"整条数据链卡死"轻。

**代价与补偿**：进程崩溃时队列中未判定的数据不产生告警，但**测量值已入库**。
补偿方式为启动时扫描近期无告警记录的测点补算，实现为可选开关，架构上预留接口位。

## ADR-06　判定状态只重建活动告警集合

**决策**：启动时查询未恢复告警初始化"已触发"集合；去抖计数从 0 开始。

**理由**：两类状态丢失的后果不对称。

| 状态 | 丢失后果 |
|---|---|
| 去抖计数 | 多等几个周期才告警，仅时延 |
| 活动告警集合 | 已告警的测点被重新计数、重新拉响，**违反"未恢复不重复告警"** |

**被否方案**：全量持久化去抖计数。为省几个周期的延迟引入高频写入与恢复逻辑，收益远小于复杂度。

**顺带的设计约束**：单消费者意味着状态为单写者，**不需要加锁**。
不要为"预留并发扩展"提前加锁——那是为不存在的问题付代价，还会让人误以为这里已支持并发。

## ADR-07　接入与适配合并为单一服务

**决策**：解析外部格式、幂等、入库、告警判定由同一个服务承担，内部按 `ingest` / `evaluate` / `state` 分模块。

**被否方案**：拆成"协议适配服务"与"业务处理服务"。

**理由**：拆分后自研服务数变 3，逼近上限（≤4），任一新需求即无余量。
更关键的是**两者之间会产生一次内部序列化**——幂等键、采集时间、质量码要穿过这条边界，
每加一个字段要改两处契约。合起来后这些共享同一份内存模型。

**防止变成上帝对象的约束**：

1. 不得定义或修改表结构（只投影到既定结构）；
2. 不得直接投递通知，只发"通知请求"（投递与重试属编排层）；
3. `ingest` 不得同步调用 `evaluate` 的求值函数，只能经有界队列投递（见 ADR-05）；
4. 三段必须能各自被单独引用与单测——**模块边界而非进程边界**，这是合并的前提。

**代价**：单进程内职责较多，靠模块边界而非进程边界隔离。

## ADR-08　展示层读写分离，只读视图持只读账号

**决策**：展示层拆成只读视图（分析）与写视图（操作）两段，只读视图使用**只读数据库账号**。

**被否方案**：

| 候选 | 落选原因 |
|---|---|
| 一体化门户（同一界面既查又改） | 只能靠开发约定约束写操作，约定会被临时需求打破 |
| 全自研 Web | 违反"平台侧复用开源"；工作量与验收风险最高 |
| BI 类工具（Metabase / Superset） | 偏探索式分析，实时刷新与大屏弱，内存更重 |
| 低代码平台（Appsmith / ToolJet） | 与现有分析视图功能重叠，镜像与内存越过轻量化 |

**理由**：只读账号是**权限层面的保证**，而非开发约定。约定会被忘记，权限不会。
这让"界面永不写坏数据"成为架构属性而非纪律要求。

**关于大屏**：不单独开发大屏。用分析视图的 kiosk 模式复用现有面板，成本近零，
且不会出现"大屏与主界面两套数据口径"的问题。

**代价**：两个入口，演示动线需在剧本里显式编排。

## ADR-09　数据分级留存（明细 7 天 / 分钟聚合 30 天）

**决策**：明细保留 7 天，分钟聚合保留 30 天，长周期曲线走聚合。

**理由**：默认规模下 140 测点 × 5 秒 × 30 天约 7250 万行，50 GB 磁盘无法承载明细。
而需求对长周期的要求是"可查询趋势"，未要求原始粒度。

**代价**：30 天曲线为聚合精度。若验收要求长周期原始粒度，需扩容并改保留策略。

## ADR-10　边缘缓存用嵌入式 KV，不用 SQLite

**决策**：嵌入式 KV（bbolt），单文件 B+ 树，按序号顺序写、顺序读。

**被否方案与落选原因**：

| 候选 | 落选原因 |
|---|---|
| SQLite | 需 CGO 或纯 Go 替代实现，二进制体积与交叉编译复杂度上升；且补传只需先进先出，不需要 SQL |
| 文件队列（自写元数据） | 元数据与一致性需自己管，易出错 |
| LSM 类存储（Badger） | 写放大明显，小数据量下收益不抵复杂度 |

**理由**：补传的访问模式就是"顺序写、按序读、按序删"，B+ 树天然契合，不需要查询能力。

## ADR-11　边缘与仿真件用不同语言

**决策**：交付件用 Go（静态二进制、无运行时依赖），仿真件用 Python。

**理由**：边缘要能部署进资源受限的终端设备，静态二进制无运行时依赖是最省心的形态；
仿真件是内部工具，Python 生态成熟、开发最快，且**不作为生产代码交付**，性能不敏感。

**附带收益**：语言不同天然阻止了"仿真件代码被交付件引用"这类越界——这不是靠纪律，是靠工具链。

**代价**：双语言，需统一日志与配置格式规范。

## ADR-12　序列化统一 JSON

**决策**：全部报文 JSON，UTF-8，中文直出。

**被否方案**：Protobuf / CBOR。

**理由**：体积小是唯一优点，但代价不可接受——客户对齐规范以 JSON 表述，
转成二进制会引入一个**客户无法核对的中间层**；同时破坏"验收时逐字段人工对照"的证据形式。
可核对性在本项目里比带宽重要。

## ADR-13　三个仿真件保持独立

**决策**：从站模拟器、数据构造器、通知接收端各自独立进程与镜像。

**被否方案**：合并为一个多模式仿真服务。

**理由**：三者服务于**三个不同的验证目的**，合并会让"这个仿真件在证明什么"变得含糊。
更重要的是验证纪律要求"证明采集能力必须走主通道"——一旦合并成单进程，
这条纪律在代码层面就失去了强制手段。

**附带考虑**：数据构造器批量生成长周期数据时内存峰值较高，与通知接收端共用进程会挤占后者，
演示中可能导致通知丢失。

**为什么虚拟串口不算第四个仿真件**：它是操作系统工具，不是自研代码，也不承载验证目的。
把它算进来会让"自研仿真件"的口径变得不可判定。

## ADR-14　配置校验做成 Go 命令，而非脚本或纯 schema

**决策**：配置校验与种子生成放进 `cmd/config-tool`，规则实现在 `internal/config`；
`config/schema/*.schema.json` 只约束形状与取值域，语义规则（V-01~V-11）由 Go 代码执行。
`make verify-config` 与 `make seed` 共用这一份实现。

**被否方案与落选原因**：

| 候选 | 落选原因 |
|---|---|
| 只用 JSON Schema + 校验器脚本 | V-03/V-05/V-06/V-07 是跨字段、跨块的语义约束（寄存器覆盖、作用域唯一），JSON Schema 表达不了；只能用 `if/then` 拼出一团读不懂的东西 |
| 写一个 Python 脚本 | 采集应用启动时也必须跑同一套校验（§6.2 拒绝启动）。脚本与 Go 两份实现必然漂移，而漂移的方向恰好是「脚本过了、进程起不来」 |
| 在 `cmd/edge-agent` 里做校验 | 种子生成也要校验，但 `make seed` 不该拉起采集进程 |

**理由**：校验规则是交付件行为的一部分，不是辅助工具。放在 Go 里，`make verify-config` 与
edge-agent 的启动校验走同一条代码路径，改一处不会漏另一处。

**代价**：CI 的 config job 需要 Go 工具链；比纯脚本慢一个数量级（本项目规模下仍 < 1 s）。
**明确接受**——CI 本来就为 Go 装了工具链。

**边界**：`internal/config` 不连数据库、不读环境变量，只读文件。投影由生成的 SQL 完成，
校验器不负责「库里是否已经一致」。
