## AC-01　全网 140 测点按 5 秒周期采集　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「性能」行；验收用例 AC-01、MV-09
- **通道**：主通道
- **前置**：10 对虚拟串口就绪，5 台终端配置与点表齐全
- **步骤**：起 5 台 `edge-agent`，连续采集 30 个周期
- **预期**：140 个测点全部产出，采集周期间隔稳定在 5000 ms ± 允许抖动；
  无测点漏采、无重复上报
- **证据**：采集周期间隔序列、每周期产出的测点计数

## AC-02　寄存器地址与点表一一对应　`[推]`

- **出处**：推导自 `tasks/004-仿真链路与点表核对.md` 的「140 点逐点可读记录」
- **通道**：主通道
- **前置**：虚拟串口与从站模拟器就绪，10 条总线全通
- **步骤**：给每个测点写全局唯一哨兵原始值，逐点读回比对
- **预期**：140 行核对记录全部一致；任何地址错位、总线串号、拆字顺序错误都会让
  读回值与预期不符
- **证据**：`docs/evidence/004/point_check.csv`

## AC-03　工程值换算正确　`[推]`

- **出处**：推导自 `tasks/005` 的换算 seam 验收（缩放、字节序、符号扩展、量程、质量码）
- **通道**：主通道
- **前置**：换算模块就绪，点表已加载；准备可写入的原始寄存器
- **步骤**：分别注入 int16 / uint16 / int32 / uint32 的边界值与负值，比对工程值
- **预期**：缩放与偏移正确；AB CD 高字在前；符号扩展正确；越界给真实质量码
  而不是沿用旧值或填 0
- **证据**：换算用例实测表

## AC-04　模拟量连续 N 次越限才告警　`[推]`

- **出处**：推导自 `tasks/010` 验收「模拟量连续 N 次越限才告警，单次波动不告警（BR-32）」
- **前置**：阈值表已载入，去抖次数 N 已按测点配置
- **步骤**：把测点值设为越限，连续采 N 次；再做一次单点波动（1 次越限后恢复）
- **预期**：连续 N 次才拉响；单次波动不告警；N 按测点配置
- **证据**：告警产生时刻与越限计数序列

## AC-05　恢复需连续 N 次不满足　`[引]`

- **出处**：`docs/07-待确认项与开放决策.md` O-08「AC-05 不通过」；
- **前置**：同 AC-04，且该测点的恢复次数与触发次数对称
  `.claude/rules/adapter-evaluate.md`「恢复条件存在文档冲突」
- **语义**：恢复与触发对称，**首次未命中就恢复是缺陷**
- **步骤**：告警触发后，让测点值回落在阈值内 1 次、再越限 1 次，循环 N-1 次；
  最后连续 N 次满足
- **预期**：中途不恢复；连续 N 次不满足才恢复。若首次未命中即恢复，
  数值抖动一次就恢复、下一周期立刻重新拉响，产生刷屏
- **证据**：状态机状态序列与恢复时刻

## AC-06　开关量当次即告警、当次即恢复，不去抖　`[推]`

- **出处**：推导自 `tasks/010` 验收「开关量当次即告警、当次即恢复，不去抖（BR-34）」
- **前置**：开关量测点（YX）已配置，不去抖
- **步骤**：开关量置 1 → 采 1 次 → 置 0 → 采 1 次
- **预期**：置 1 当次拉响、置 0 当次恢复，不累计次数
- **证据**：告警与恢复时刻与采集时刻对齐

## AC-07　高高限触发时闭合同测点的高限活动告警　`[推]`

- **出处**：推导自 `tasks/010` 验收
- **前置**：同一测点的 `HIGH_LIMIT` 与 `HIGH_HIGH_LIMIT` 阈值均已配置
- **步骤**：先让测点越过高限产生 `HIGH_LIMIT` 活动告警，再继续越过高高限
- **预期**：`HIGH_HIGH_LIMIT` 拉响时，同测点的 `HIGH_LIMIT` 活动告警被闭合；
  同一去重键只允许一条活动告警
- **证据**：`alarm` 表的 `status` 与 `ux_alarm_active` 约束下的行数

## AC-08　质量非 GOOD 不参与告警求值　`[推]`

- **出处**：推导自 `tasks/010` 验收「质量非 GOOD 不参与求值，在入口即返回（BR-18）」
- **前置**：质量码可注入（模拟器故障注入或换算侧构造）
- **步骤**：制造质量码 1~8 的读数（含越限值），观察是否产生告警
- **预期**：质量非 0 的读数在判定入口即返回，不产生告警、不推进去抖计数
- **证据**：告警表无新增行，去抖计数不变

## AC-09　断开上行后采集不中断，数据进本地队列　`[推]`

- **出处**：推导自 `tasks/007` 验收「断开 Broker 后采集不中断，数据进本地队列（BR-19）」
- **通道**：主通道
- **前置**：Broker 可停；本地队列路径与三上限已配置
- **步骤**：停 Broker，持续采集 ≥ 5 个周期
- **预期**：采集周期间隔不受上行影响；报文进本地队列，`cacheDepth` 单调增长
- **证据**：采集周期间隔序列 + 队列深度序列（`docs/evidence/007`）

## AC-10　三上限任一先到即生效，达上限 FIFO 丢最旧并上报　`[推]`

- **出处**：推导自 `tasks/007` 验收「三上限任一先到即生效（BR-20）」
- **前置**：三上限可压到可触发的值（改 `.env` 的 `CACHE_MAX_*`）
  「达上限 FIFO 丢最旧、每满 1000 条上报 CACHE_DROPPED、不得静默（BR-21）」
  「任一维度达 80% 上报 CACHE_WARNING（BR-22）」
- **步骤**：分别把时长 / 条数 / 磁盘上限压到可触发的值，制造积压
- **预期**：7 天 / 30 万条 / 512 MB 三上限任一先到即裁剪；FIFO 丢最旧；
  每满 1000 条上报一次 `CACHE_DROPPED`；任一维度达 80% 上报一次 `CACHE_WARNING`，
  同级不重复
- **证据**：裁剪前后队列统计与事件序列

## AC-11　断网不丢：持久队列跨重启，PUBACK 才出队　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「可靠性」行 `AC-11~AC-13`
- **通道**：主通道
- **前置**：本地队列已落盘（`-cache` 指向真实文件）；进程可杀可起
- **步骤**：断网期间积压 → 杀进程 → 重启 → 观察出队时机
- **预期**：重启后队列条数不丢；收到 PUBACK 才出队，超时未确认不出队
- **证据**：重启前后队列条数、出队与 PUBACK 的时刻对应

## AC-12　恢复不重：补传后实时值不回退　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「可靠性」行；
  `tasks/_TEMPLATE.md` 的验收写法示例「AC-12：补传 500 条后
  `realtime_value.collect_time` 未回退」
- **通道**：主通道
- **前置**：积压 ≥ 500 条可制造；`realtime_value` 有基线行
- **步骤**：补传 500 条后查实时值
- **预期**：`realtime_value.collect_time` 未回退——只被更晚 `collectTime` 覆盖；
  幂等门挡住重复报文，历史表不出现重复行
- **证据**：补传前后 `realtime_value` 的 `collect_time` 对比

## AC-13　恢复后按 seq 正序补传，collectTime 保留　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「可靠性」行
- **通道**：主通道
- **前置**：Broker 可停可起；订阅端可收补传报文
- **步骤**：断网积压 N 条 → 恢复 → 收集补传报文
- **预期**：`seq` 严格正序（跳号允许、重号禁止）；`collectTime` 保留原值；
  `sendTime` 更新为补传时刻；`backfill=true`
- **证据**：补传报文的 seq / collectTime / sendTime / backfill 序列

## AC-14　实时值只进不退　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「一致性」行
- **前置**：`realtime_value` 有该测点的基线行，含 `collect_time`
- **步骤**：先写较新 `collectTime` 的读数，再写较旧 `collectTime` 的读数
- **预期**：实时值不被较旧的读数覆盖。条件写在 SQL `WHERE` 里，
  不在应用层先查后写
- **证据**：写入前后 `realtime_value` 的 `collect_time` 与 `value`

## AC-15　按终端隔离发布权限　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「安全性」行
- **前置**：MQTT 账号与库角色已按 `deploy/mosquitto/acl.*` 配好
- **步骤**：用终端 A 的凭据发布终端 B 的主题；查库角色权限
- **预期**：越权发布被拒（注意：只有 `-V mqttv5` 下才返回 `Not authorized`，
  3.1.1 的退出码是 0）；库角色按权限矩阵隔离，只读账号无写权限
- **证据**：拒绝日志、权限矩阵核对（`docs/evidence/` 的 broker 验证记录）

## AC-16　补传限速，且不拖慢采集　`[推]`

- **出处**：推导自 `tasks/007` 验收「补传单批 ≤ 500 条、批间隔 ≥ 50 ms（BR-24）」
  「补传期间采集协程不停（BR-25）」
- **通道**：主通道
- **前置**：积压足够多，可制造多轮补传；采集周期可观测
- **步骤**：压低批量上限制造多轮补传，观察每轮条数与采集周期
- **预期**：每轮 ≤ 500 条、批间隔 ≥ 50 ms；补传期间采集周期间隔不变
- **证据**：补传轮次的条数序列、补传期间的采集周期间隔

## AC-17　落库幂等　`[推]`

- **出处**：推导自幂等 seam 的既定验收（首次 true、重复 false、冲突时不写业务表）
- **前置**：幂等表可查；同一 `msgId` 可重复投递
- **步骤**：同一 `msgId` 投递两次
- **预期**：首次判重通过、重复判重拒绝；判重在写任何业务表之前；
  重复投递不产生重复历史行
- **证据**：幂等判重结果与业务表行数

## AC-18　通知触达：卡片字段、分流、重试、留痕　`[推]`

- **出处**：推导自 `tasks/011` 的 10 条验收
- **前置**：Node-RED 流程已部署，接收端可投递；`notify_log` 可查
- **步骤**：分别投递 level 1 / 3 的告警；制造一次通道不可达
- **预期**：卡片含车间、终端、设备、测点、级别、触发值、发生时间、告警原因；
  level 1 只入库不发通知，level 3 立即发；失败按 1/5/15 秒共 4 次；
  成功与失败都写 `notify_log`；通知失败不阻塞告警落库
- **证据**：`docs/evidence/011/acceptance.json`

## AC-19　改配置不改代码　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「可配置性」行
- **前置**：各配置文件与生效边界已知；`git` 工作区干净以便证明无代码改动
- **步骤**：改点表地址 / 阈值数值 / 主题模板 / 串口参数 / 通知通道地址，
  不改代码
- **预期**：按各自生效边界生效（阈值 60 秒热加载、点表重启生效等）；
  切换通知通道只改 `WECOM_WEBHOOK_URL`
- **证据**：改配置前后的生效观测、代码无改动（`git diff`）

## AC-20　换协议不影响其他组件　`[引]`

- **出处**：`docs/01-概要设计说明书.md` §10「可替换性」行
- **前置**：`make lint` 可跑；三条冻结线的边界已明确
- **步骤**：核对 Codec 与 Sink 的接口边界，及三条冻结线的隔离
- **预期**：换协议实现只影响 `internal/agent` 的 codec，不影响判定与入库；

- **证据**：import 边界检查（`make lint` 的 depguard）、接口清单
