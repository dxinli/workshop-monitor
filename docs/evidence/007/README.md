# 007 本地缓存与补传 · 验收证据

## 结论

5 条用例全部通过。`acceptance.json` 由 `scripts/accept-007.py` 生成，命令见任务单。

## 链路

主通道：从站模拟器 → 虚拟串口 → `edge-agent` → Mosquitto → 订阅端。
补传是**跨进程**能力（进程重启后队列还在），所以验收真停 Broker、真重启进程，
不在单测里 mock 连接状态。

## 逐条证据

| 用例 | 实测 |
|---|---|
| 断开 Broker 后采集不中断，数据进本地队列 | 断网 22 秒内 5 个采集周期，间隔 `[5025, 4999, 5001, 5000]` ms；10 条报文入队 |
| 重启后队列仍在，恢复联网按 seq 正序补传 | 断网期间入队 6 条；重启后订阅端收到 `backfill=true` 6 条，seq 正序、`collectTime` 保留、`sendTime` 更新 |
| 补传单批不超上限 | `BACKFILL_BATCH=2` 时补传分 5 轮、每轮恰好 2 条（10 条入队） |
| 发布失败不出队 | Broker 全程不可达时补传一次都没发出去，队列文件保持 65536 字节；恢复后补出 6 条 |
| 三上限取冻结值 | 7 天 / 300000 条 / 536870912 字节（512 MB） |

## 实物观测（人工复核过的一次完整断连-恢复）

停 Broker 期间：`入队 9 条`、`采集周期 12` 个、周期间隔 `[5000, 4999, 5005, 5000, 5001]` ms
——采集完全没有被上行拖慢（BR-25）。

重启后补传：`补传一轮完成 sent=9`，订阅端收到 15 条中 9 条 `backfill=true`，
首条 `collectTime=1793495858427` 保留原值、`sendTime=1793495901523` 更新为补传时刻
（差约 43 秒，正是断网时长）。

## 三处容易误判的细节

1. **补传的判据是 `backfill=true`，不是「时间差很大」。** 用时间差判断会把慢上报误判成补传
   （详细设计 E-08）。
2. **验收里把 `BACKFILL_BATCH` 压到 2 是为了能在二十秒内看出「分几轮」。** 500 条的默认值
   在演示规模下每轮都装不满，看不出上限行为。
3. **缓存类事件（`CACHE_DROPPED` / `CACHE_WARNING`）失败时不落队列。** 它们描述的就是队列
   自身状态，塞回满队列会自我递归。这条只在单测里验，端到端不构造。
