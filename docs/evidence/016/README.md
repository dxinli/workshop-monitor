## 这一轮踩出的坑（都已修，留在这里防下一个人）

跑批脚本的判据本身有 6 处缺陷，全是**实跑暴露**的，不是预判。
其中两处是**判据作弊**——会让验收看起来通过，比功能 bug 更危险：

1. **`psql` 吞掉 stderr。** SQL 失败只表现为「造 0 行」，看着像策略生效了——
   假阴性伪装成成功。改失败即抛。
2. **聚合手算列名错。** `measurement_1m` 是 `bucket` / `point_id` / `si_type`，
   没有 `bus_id` / `slave_addr` / `point_code`，且只对 `quality = 0` 求均值。
3. **`run_job` 与 `refresh_continuous_aggregate` 是过程不是函数。** 写 `SELECT` 会被
   报 `is a procedure`。
4. **`drop_chunks` 按整块删、不按行删。** 物化超表 10 天一格，插 31 天前的行落在
   09-24~10-04 那格里，块尾没过 30 天线，策略**合法地不删它**。改插 50 天前留够
   余量，并用独有 `seq` 区间当标记行计数，不靠时间阈值——时间阈值会把别人留下
   的旧行也算进判据。
5. **补传验证查错了表。** `backfill` / `collect_time` 在 `measurement` 上，
   `raw_message` 没有这两列。旧代码那条「ok 补传验证」是**假阳性**。
6. **seq 归零被判重，链路整段不出数**（AGENTS.md「序号不归零」那条铁律的反面）。
   `_tmp` 每轮跑完清掉，seq 高水位跟着没，下一轮 agent 从 1 重发，而幂等门里
   那些 `msgId` 早被上一轮用过——整段判 `DUPLICATE`，一行都进不了库。
   现象是「链路就绪、采集周期完成、库里的行数一动不动」，极难往序号上想。
   修复：起 agent 前把 seq 高水位从 `max(seq)` 续接。

另有三处判据口径也纠了：

- **抽样核对比最新一条，不比窗口 max。** 窗口里还留着哨兵写入前的量程中点 90，
  取 max 会让哨兵写没写都一样。
- **时间轴检查按「视图承载业务时间轴吗」判。** `v_raw_recent` 按 `receive_time`
  排序**正是它的用途**（最近收到的原始报文，运维视图），不是业务时间轴的违例。
- **补传的「collectTime 是原时刻」用平均滞后判，不用逐行判。** 断网末尾采到、
  恢复后立刻补传的行滞后天然就小（实测 700 行滞后 ~18 秒），逐行设阈值必然误报
  边界行；而实现若把 collectTime 写成恢复时刻，**平均滞后会趋近 0**。

还加了一道前置断言：**跑检查前先确认链路真的在产出**（20 秒内行数增长）。
没有它，每条检查都可能读到上一轮的旧值而误判通过——「抽样核对」就发生过：
读到的是上一轮哨兵写入的 62.5，链路其实一行都没产出。

聚合验证走公共 API `CALL refresh_continuous_aggregate`，**不写
`_timescaledb_internal` 的物化超表**——那个表名带内部编号，重建后就变，
往里插是拿实现细节当接口。
