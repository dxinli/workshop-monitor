## 偏差

原计划对接真实企业微信群机器人。当前无凭据（O-03 待确认），改为对接 `sim/wecom-mock`，
验收从"真实群收到消息"改为"接收端按企业微信卡片格式正确渲染并留痕"。
凭据到位后只改 `.env`，不动代码。

1. **接收端容器化进 Compose `sim` profile，不再用宿主机 venv 形态。**
   019 交付的是宿主机 venv（沿用 004 的做法），但 Node-RED 在容器里，
   容器内的 `localhost` 是容器自己，投递会连到不存在的端口——这就是 O-19。
   本任务补 `sim/wecom-mock/Dockerfile` 与 compose 服务，容器间走服务名
   `wecom-mock:8081`，与接口规范附录 B 的默认值一致。
   **O-19 就此关闭**（`../docs/07-待确认项与开放决策.md`）。

2. **`deploy/versions.env` 新增 `PYTHON_SIM_VERSION=3.12.7-slim-bookworm`。**
   镜像标签的唯一来源是 versions.env，新镜像必须在此登记。这是「新增条目」
   不是「改版本号」，且属于上一条容器化方案中已确认的一部分。
   `AGENTS.md` 的 Python 版本口径（3.12.7）未变。

3. **`WECOM_ENABLED` 的取值只认字面量 `false` 关闭。** 空串、未设置、任何其它
   取值都视为开启，与 adapter 侧 `NOTIFY_ENABLED`（`cmd/proto-adapter/evaluate.go`
   的 `!= "false"`）同一口径。理由：把「没填」误判成「关」会让通知静默消失，
   而这正是本任务要防的那类故障。

4. **`WECOM_ENABLED` 必须显式进 compose 的 node-red 环境块。**
   少了那一行 `env.get` 读到空串，灰度开关永远不生效，现象是「怎么关都投」，
   演示现场很难查。已在 compose 里落 `WECOM_ENABLED: ${WECOM_ENABLED:-true}`。

5. **`check-notify.sh` 的连通检查用 GET 打 `/webhook`，回 405 判 ok。**
   接收端只收 POST。有没有 HTTP 响应才分得开「连得上但方法不对」和
   「根本连不上」——后者才是本任务要防的故障。输出里注明「仅证明链路通」。

6. **`make check` 与 CI 的 pytest 目标不变**（019 已扩到 `sim`）。本任务未加
   仿真件单测：灰度开关是 Node-RED 函数节点里的分支，能验的只有端到端。
