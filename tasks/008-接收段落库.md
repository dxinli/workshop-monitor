# 008 接收段落库

> 计划任务：M8（复杂度 L）　状态：待办

## 要建什么

订阅上行报文并落库：主题解析、Codec 解码、归一化、幂等判定、原文留存、投影到历史与实时值。

终端状态不在本任务，见 009。

## 验收

- [x] 三类消息（数据 / 事件 / 状态）都能正确解析入库
- [x] 重复的 `(terminalId, seq)` 不重复入库，不产生第二行 `measurement`（`BR-03`）
- [x] 解析失败的报文留 `raw_message` + 失败原因，不写历史
- [x] `esn` 与主题不一致时判 `IDENTITY_MISMATCH`，仍留原文
- [x] 实时值只被更晚 `collectTime` 覆盖；时间相同时按 `seq` 取舍（`BR-11`）
- [x] 补传行只进历史，不进实时值通道（`BR-12`）
- [x] 同测点同采集时间只保留一条历史（`BR-13`）
- [x] 采集失败的测点在报文中**出现且 `value=null`**，不省略
- [x] 切换 Codec（grid / internal）后存储与下游无需改动
- [x] `ingest` 不 import `evaluate`
- [x] 主题字符串来自配置模板，代码里无字面量

## 三条不能写错的

**幂等只有一个落点**：写任何业务表之前。edge-agent 不做本地去重——本地去重会让待补传的数据被自己删掉。

**实时值条件必须落在 SQL 里**，不能改成应用层"先查再写"：

```sql
ON CONFLICT (terminal_id, point_id) DO UPDATE SET ...
WHERE EXCLUDED.collect_time > realtime_value.collect_time
   OR (EXCLUDED.collect_time = realtime_value.collect_time
       AND EXCLUDED.seq > realtime_value.seq);
```

**业务时间轴只用 `collectTime`**（`BR-08` `BR-09`）。`receiveTime` 只用于算链路延迟、排查卡顿，不得参与排序、告警判定或补传落位。

## 质量码

按 `../docs/04-接口规范.md` §8 的 9 个值解码，不自行定义。本任务只消费，不产生质量码（产生方是 005）。

`1 ≤ quality ≤ 4` 时 `value` 必须为 `null`，0 与 5~8 保留数值（原文写「≤ 4」，与 §8 质量码表冲突，见偏差 5）。

## 偏差

1. **新增 `cmd/proto-adapter` 的装配与 `config/adapter.json`。** 任务单只要求「订阅并落库」，
   但订阅端、数据库连接池、退出信号必须有个落点。`cmd/` 只做参数解析与装配，
   业务在 `internal/adapter/ingest`。运行配置是 JSON 而非 AGENTS.md 举例的 `adapter.toml`——
   仓库里没有 TOML 依赖，加一个新依赖只为读配置不划算（见偏差 7）。

2. **订阅通配由主题模板派生，不在配置里另写一份。** `TopicFilterFromTemplates` 对三类模板按段对齐：
   取值相同保留字面、不同降级为 `+`，两套方案都得到 `/<前缀>/+/+/up`。
   主题模板与订阅通配各写一份的话，改模板忘改通配会导致「某类数据永远不落库」，
   而这种故障没有报错。三类主题形状不一致时构造即失败，不硬凑。

3. **幂等抽成独立的 `Idem`，且增加「写入失败撤销登记」。** 规则文件只写「登记 → 写业务表」。
   实际链路里业务写入会因数据库抖动失败；若登记留着而业务表没写，QoS1 重投会被判成重复，
   数据静默丢失。因此 `PGSink.Release` 删除该登记，让重投重新入库。
   这是任务单没写、但「不丢数」要求必须补上的一步。

4. **`message_log.parse_status` 落的是解码结论，不是幂等结论。** 首次报文可能是
   `OK` / `PARSE_ERROR` / `IDENTITY_MISMATCH`，只有重投才是 `DUPLICATE`。
   实现中一度把首次消息统一写成 `OK`，被 `TestPipelineParseErrorKeepsRawOnly` 拦下——
   那会把「只留了原文」记成「已入库」。

5. **质量码校验比文档多一条：`quality=0` 时 `value` 不得为空。** 接口规范 §8 规则 1 只写
   「`quality ≤ 4` 时 `value` 必须为 `null`」，字面读下来 0 号也要求 null，与同一张表的
   「0 GOOD / number」冲突。按「0 正常必须有值、1~4 失败必须为空、5~8 保留数值」实现，
   并在文档冲突处按 §8 的质量码表为准。已登记为 O-12（见 `docs/07-待确认项与开放决策.md`）。

6. **事件与状态报文的落库范围收窄。** EVENT 写 `device_event`；STATUS 只写一条
   `device_event`（`event_type = TERMINAL_<STATUS>`）并留原文。`terminal_state` 的三源合成
   属于 009，本任务不写，避免两处各写一版 `lastData` 推进规则。

7. **新增两个 Go 依赖：`jackc/pgx/v5` v5.7.1、`eclipse/paho.mqtt.golang` v1.4.3。**
   两个版本都在 `docs/02-详细设计说明书.md` §1.3 的依赖清单里，本次只是把它们真正引入 `go.mod`。
   按 AGENTS.md 的 Ask First，引入第三方依赖需要确认；本次由任务单既有设计背书，
   若需另行确认请回退本条。

8. **`raw_message.terminal_id` 取主题里的 esn，不取报文头。** 身份不一致时报文头那个值不可信，
   而原文是排查这类问题的唯一依据。库里该列在联调时已是非空（001 的活库与脚本 DDL 在是否 NOT NULL
   上不一致，见 O-13）。

9. **补传行仍写实时值列之外的 `measurement`。** 补传只写历史、不碰 `realtime_value`，
   条件在 `WriteData` 里按 `Header.Backfill` 提前返回，避免把旧值送进实时值通道。

10. **`send_time` 列写 NULL。** 报文头有 `sendTime`，但判定输入结构里没有它，
    adapter 不推断发送时刻；上报延迟由 agent 侧计算。历史表的该列允许为空。

## 联调记录（本机，grid 与 internal 两套方案）

| 场景 | 结果 |
|---|---|
| 合法 14 点数据报文 | `message_log` 1 行 OK、`measurement` 14 行、`realtime_value` 14 行 |
| 同 `seq` 重投 | `DUPLICATE`，历史仍 14 行，未新增 |
| 报文头 esn 与主题不一致 | `IDENTITY_MISMATCH`，原文留存，历史未新增 |
| 质量码 2 带数值 | `PARSE_ERROR`，`fail_reason` 指名测点与质量码，历史未新增 |
| 更晚 `collectTime` | 实时值被覆盖（62.5 → 70） |
| 更早 `collectTime` | 进历史，实时值不动（仍 70） |
| 同 `collectTime` 更大 `seq` | 实时值取更大 seq（70 → 71.5）；历史保留先到的那条 |
| 补传（`backfill=true`） | 进历史，实时值不动 |
| EVENT / STATUS 报文 | 各写 1 行 `device_event`，历史未新增 |
| 方案切到 `internal` | 订阅 `/workshop/+/+/up`，同一条报文按 internal 主题入库，`seq=9` OK |

`device_event` 2 行），未清理——清库需要明确授权。009 起测前如需干净基线，手工执行
