# 007 本地缓存与补传

> 计划任务：M7（复杂度 L）　状态：已完成
>
> 端到端验收在宿主机 venv 形态下执行，见「偏差」

## 要建什么

上行失败时落盘、三上限裁剪、恢复后按序限速补传。用 bbolt 做本地持久化。

## 验收

- [x] 断开 Broker 后采集不中断，数据进本地队列（`BR-19`）
- [x] 三上限任一先到即生效：7 天 / 30 万条 / 512 MB（`BR-20`）
- [x] 达上限按 FIFO 丢最旧，每累计 1000 条上报一次 `CACHE_DROPPED`，不得静默（`BR-21`）
- [x] 任一维度达 80% 上报 `CACHE_WARNING`，同级别不重复上报（`BR-22`）
- [x] 恢复后按序号正序补传，保留原 `collectTime`、更新 `sendTime`、`backfill=true`（`BR-23`）
- [x] 补传限速：单批 ≤ 500 条、批间隔 ≥ 50 ms（`BR-24`）
- [x] 补传期间采集协程不停（`BR-25`）
- [x] 收到 PUBACK 才出队；超时未确认不出队（`BR-26`）
- [x] `cache.trim` 有测试覆盖三上限触发与丢弃计数

## 偏差

`backfill` 是报文头布尔字段，不是质量码——补传报文的测点质量码仍是 `GOOD`。

1. **新增依赖 `go.etcd.io/bbolt` v1.3.11。** 版本早锁在 `AGENTS.md` Tech Stack 与详细设计 §1.3
   的依赖清单里，本任务按既有设计引入，未改版本号。按 Ask First 属「新增第三方依赖」，
   已获确认后执行。

2. **额度用尽式裁剪会丢已采集的数据，这是设计内的取舍。** 三上限任一触顶就 FIFO 丢最旧，
   丢的是「还没发出去的报文」。接口规范 §9.4 就是这么定的；`CACHE_DROPPED` 事件保证
   丢弃有留痕（每满 1000 条一次），不会静默。

3. **补传失败时本轮立即返回，不继续发后面的。** 同一轮里后续报文大概率也发不出去，
   连发只会把失败排成一串、刷满日志。下一轮从同一条重试。`retryCount` 字段已落盘，
   但**本轮不做重试次数上限**——补传该一直重试到成功或报文被裁剪掉，
   这与「不要无限重试」不冲突：那条规则针对的是单次请求内的重试（Modbus 2 次、CRC 1 次），
   不是跨周期的补传。

4. **报文无法改写（JSON 坏掉）时丢弃并记 Error 日志。** 留着只会每次补传都失败一次，
   永远出不了队，还会占着三上限的份额。

5. **`cacheDepth` / `cacheBytes` 现在报真实值。** 006 时因为没有队列报 0，
   本任务起状态报文里的两项来自 `Cache.Stats()`；`agentVersion` 与其余字段不变。

6. **顺手修掉 006 留下的缺陷：数据发不出去时事件判定被跳过。**
   原实现 `SendBatch` 在 `sendData` 失败时直接返回，设备失败计数根本不推进，
   断网期间永远攒不出 `SENSOR_OFFLINE`。现在事件判定提到发布之前，
   数据失败不影响事件入队。回归测试 `TestDeviceFailuresCountedEvenWhenBrokerDown`
   留在仓库里。

7. **缓存类事件（`CACHE_DROPPED` / `CACHE_WARNING`）失败时不落队列。**
   这两个事件描述的就是队列自身的状态，把它们塞回满队列会在
   「满 → 丢 → 发事件 → 入队 → 又满」之间自我递归。发不出去就只记日志。
