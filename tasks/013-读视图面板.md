## 偏差

1. **`grafana` 服务首次加进 `deploy/docker-compose.yml`。** 任务单只要求面板与 provisioning，
   但 compose 里此前根本没有 Grafana——没有容器就没有"数据源走 provisioning"的落点。
   镜像标签取 `deploy/versions.env` 已有的 `GRAFANA_VERSION`，未新增版本条目。

2. **Grafana 以只读形态运行：匿名访客 + Viewer + 不建管理员。**
   `workshop_readonly` 只给到数据库层，Grafana 自身仍有"谁登录谁改面板"的问题。
   因此关登录表单、关初始管理员创建、匿名访客给 Viewer，任何写请求返回 403；
   默认 `admin/admin` 登录返回 401。配置写入面板不生效（`allowUiUpdates=false`），
   改动只能落到 JSON 并提交——这与「不要只在界面改面板」是同一条规则的两端。
   代价是部署后没有管理员入口，需要改配置时改 compose 环境变量重启。

3. **≤24h 查明细、>24h 查聚合，两条分支写进同一条 SQL。** 时间范围变量只有 1h/24h/7d/30d 四档，
   但 PostgreSQL 无法在一条 SQL 里按参数选表。做法是把两条分支 `UNION ALL` 起来，
   各自带一个 `One-Time Filter`：`(SELECT EXTRACT(EPOCH FROM ($__timeTo() - $__timeFrom()))) <= 86400`。
   `EXPLAIN ANALYZE` 显示不成立的那一支被剪掉（`never executed`），因此 30 天窗口不会扫明细。
   这是用 SQL 表达"按范围选源"的唯一不引入写逻辑的办法；证据见 `docs/evidence/013/plan-30d.txt`。

4. **视图没有配套新视图，列缺的用字典表补。** `v_realtime` 不带 `point_code`（开关量的 0/1 要按
   point_code 翻译成「打开/按下/遮挡」），`v_alarm_history` 只含 alarm 本表列（车间与设备名要从
   `v_point_dict` 或 `terminal` 补）。按「改表结构先确认」的规则，本任务没动 `deploy/timescaledb/init/`，
   改在面板 SQL 里 JOIN 字典。若后续要收敛，应另开任务把这两列加到视图。

5. **能耗曲线按车间汇总，不按测点。** 接口规范 §13.3 的口径是"有功功率汇总求和、电能末值差"，
   按测点画 5 条曲线没有可加性（不同测点的 ep_forward 是各自独立的累计量）。
   面板按车间出曲线；测点级原始值在历史曲线页选点看。

6. **导出用「数据明细」表的 Inspect → Download CSV，不另做导出按钮。** Grafana 的 panel CSV
   导出走同一条查询，不额外实现下载端点。时间列用 `to_char(... AT TIME ZONE 'Asia/Shanghai',
   'YYYY-MM-DD HH24:MI:SS.MS')` 在 SQL 里格式化成文本，保证 CSV 里不是 epoch（§13.2）；
   `value` 为 NULL 时导出空串，不导出 0。单次上限 20 万行写进 `LIMIT`。

7. **新增 `scripts/verify-read-view.sh` 与 `make verify-read-view`。** 逐条对应验收项：
   面板可读、写接口 403、数据源账号、刷新/时区/时间范围、132 条查询在四个时间范围下可执行、
   30 天执行计划、最近正常值列、配电术语、能耗口径。走 Grafana 自己的 `/api/ds/query`，
   验证的是界面上真正跑的 SQL。`make check` 不含它——需要全栈在跑。
