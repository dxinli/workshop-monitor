## 质量码

权威定义在 `../../docs/02-设计/04-接口规范.md` §8（冻结线 A）。固定 9 个值，不得增删改名，不得用字符串字面量散落代码：

| quality | 名称 | value 规则 | 方向 |
|---:|---|---|---|
| 0 | `GOOD` | number | 边缘产生 |
| 1 | `DEVICE_EXCEPTION` | null | 边缘产生 |
| 2 | `TIMEOUT` | null | 边缘产生 |
| 3 | `CRC_ERROR` | null | 边缘产生 |
| 4 | `PARSE_ERROR` | null | 边缘产生 |
| 5 | `OUT_OF_RANGE` | **保留数值** | 边缘产生 |
| 6 | `STALE` | number / null | 平台侧判定，**边缘不产生** |
| 7 | `SIMULATED` | number | 仿真件 |
| 8 | `MANUAL` | number | 仿真件 |

`quality ≤ 4` 时 `value` 必须为 `null`；`5~8` 保留数值。

> 原文「≤ 4」把 0 号（`GOOD`）也包含进去了，与同一张表的「0 `GOOD` / number」冲突。
> 实现按质量码表执行：0 必须有值、1~4 必须为空、5~8 保留数值。该冲突见 O-14（008 已先登记）。

**两个易错点**

- 补传不是质量码。它是报文头 `backfill` 布尔字段，与 `quality` 正交（`BR-17` 把它列进质量标识是业务口径，实现必须落到 `backfill`）。
- 超时是 `TIMEOUT`，不是 `COMM_TIMEOUT`。

## 三个时间（`BR-06` `BR-10`）

| 字段 | 产生方 | 只能用于 |
|---|---|---|
| `collectTime` | 本任务 | 业务时间轴：曲线、告警判定、排序、补传落位 |
| `sendTime` | 006 | 计算上报延迟、判断是否补传 |
| `receiveTime` | 008 | 计算链路延迟、排查卡顿 |

统一 int64 毫秒时间戳。三个时间不得互换，平台不得用接收时间补齐采集时间。

## 偏差

1. **新增 `internal/pkglog` 与两个 Go 依赖：`goburrow/serial` v0.1.0、`rs/zerolog` v1.33.0。**
   `internal/pkglog` 在 002 时就已建目录（只有 `.gitkeep`），两条依赖都写在
   `AGENTS.md` Tech Stack 与详细设计 §1.3 的依赖清单里，版本号未改。按 Ask First 属「新增依赖」
   与「新增共享包」，本任务按既有设计背书引入；若要另行确认请回退本条的两次 chore 提交。

2. **`pkglog` 只被 edge-agent 使用，`cmd/proto-adapter` 仍是手拼 logfmt。** 把 adapter 也切过来
   属跨组件改动，不在本任务范围。两条路径的字段名相同（`ts`/`level`/`svc`/`inst`/`msg`），
   切换时只改输出器，不动调用点语义。已登记为 O-16。

3. **新增 `config.ValidateTerminal`，只跑 V-01~V-09。** 启动校验要拒绝启动并输出具体字段，
   而 `config.Validate` 是「整份配置」的入口：它会跑 V-10（5 终端 / 10 总线 / 140 点的规模核对）
   与 V-11、主题模板校验。单台终端启动时 V-10 必然不满足，V-11 与主题模板这两份文件 agent 根本不读。
   规则本身没改，只把「单终端」这一入口暴露出来。

4. **串口端点外部化：新增 `-ports` 参数与 `.pty/agent-ports.json`。** 点表里的 `port` 是现场
   设备名（`/dev/ttyV0`），仿真的真实端点在 `scripts/setup-pty.sh` 生成处，键为 `{terminalId}.{busId}`。
   端点不写进点表：点表是冻结线 A 的契约，端点是部署事实。给端点表时缺任一条**直接报错**
   而不是回落到点表值——回落的表现是「总线全超时」，与真故障分不开。

5. **采集产出是 `agent.Batch`，经 `agent.LogSink` 输出为周期聚合日志。** 任务单要求「产出通过日志观察」，
   但没有上报段（006），也没有序号（006）。`Batch` 不含 `seq`，`LogSink` 是可替换的 `func(Batch)`，
   006 起串在它前面即可，采集循环不用改。

6. **超量程计入 `bad` 而不是 `good`。** 质量码 5 的值是可读的，但它不是正常读数；
   计入 `good` 会让「这一批全好」掩盖越限。`good`/`bad` 只按质量码 0 与非 0 分。

7. **帧格式不符（半帧、字节数越界）判 `PARSE_ERROR`(4)，不是 `TIMEOUT`。** 接口规范 §3.6
   把「帧长度或格式不符」单列为 4 号质量码。一个字节都没收到才是超时（2 号，可重试）；
   收到半帧说明设备响应了但线不好，两者混成一个码会让现场无法定位。

8. **重试次数按错误类型分开：超时用点表 `retryCount`（=2），CRC 固定 1 次，异常码与帧格式不重试。**
   依据 `rules/edge-agent.md` 的错误与质量码表。设备异常应答重试不会让从站改变答复，
   帧格式不符也不是重发能解决的。

9. **验收脚本自带一段日志解析，不复用 go 侧代码。** 期望值全部是手算字面量
   （625 → 62.5、`0x0012D687` → 12345.67 等），从模拟器写值到日志读回走的是真实链路。
   照抄实现算出来的期望永远不会失败，等于没验。

10. **`internal/agent` 的 `Batch`/`PointReading` 没有复用 `internal/model` 的点值结构。**
    `model.PointValue` 是上行报文形状（`value` 为指针、带 `unit`/`quality`），本任务的批次要带上
    `siType` 供后续按 YC/YX 分组，且此时还没有报文头。等 006 拼报文时做一次显式映射，
    比现在让采集侧迁就报文形状更清楚。

11. **`/healthz`、本地队列、MQTT 未实现。** 分别属 007、006、015，本任务不做预判式实现。
