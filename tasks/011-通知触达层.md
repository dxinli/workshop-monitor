# 011 通知触达层

> 计划任务：M10（复杂度 M）　状态：已完成

## 要建什么

Node-RED 流程 N-01（接收通知请求、按级别分流、组装卡片）与 N-02（HTTP 投递、重试、写投递日志）。

## 验收

- [x] `POST /api/notify` 收到请求后组装卡片，含车间、终端、测点、级别、触发值、发生时间、告警原因（`BR-40`）
- [x] level 1 只入库不发通知；level 3/4 立即发（`BR-39`）
- [x] 投递失败按 1 / 5 / 15 秒重试，共 4 次，末端记失败原因并终止（`BR-41`）
- [x] 成功与失败都写 `notify_log`
- [x] 编排层不可达时 adapter 告警照常入库（adapter 侧不重试）
- [x] 参数校验失败返回 400 / 422，且**不写投递日志**
- [x] 不改写 `notifyId`
- [x] `flows.json` 从编辑器导出后提交，无 flow context 持久化
- [x] 不做阈值求值、去抖、告警状态判定

## 级别与通知策略

权威定义在 `../../docs/02-设计/04-接口规范.md` §11.3：

| level | 中文 | 通知策略 |
|---:|---|---|
| 1 | 提示 | 仅入库，不发通知 |
| 2 | 警告 | 入库 + 通知（5 分钟合并） |
| 3 | 严重 | 入库 + 立即通知 |
| 4 | 紧急 | 入库 + 立即通知（置顶） |

**level = 2 的 5 分钟合并本期不实现**（落点未定，见开放项 O-09：`../docs/07-待确认项与开放决策.md`）。按立即通知处理，不要 adapter 与 Node-RED 各写一版。

## 交付

```text
deploy/node-red/
  Dockerfile      官方镜像 + node-red-contrib-postgresql（锁补丁号）
  settings.js     运行配置，无 context 持久化
  flows.json       N-01 + N-02 两个流程，编辑器导出后提交
scripts/verify-notify.sh   验收脚本，make verify-notify
```

流程节点：

```text
N-01  POST /api/notify → 校验入参 ─┬─ 400/422 → 响应（不写库）
                                   └─ 查重 + 卡片元数据 → 判定 ─┬─ DUPLICATE/未知测点 → 响应
                                                                └─ 组装卡片 ─┬─ level 1 → SKIPPED
                                                                             └─ level 2~4 → ACCEPTED
N-02  投递 → 结果 ─┬─ 2xx → 写 SENT
                   └─ 失败 → 重试判定 ─┬─ 还有次数 → 1/5/15 秒后重投
                                       └─ 用完 → 写 FAILED
```

## 偏差

1. **参数校验失败不写投递日志是反直觉但正确的**——没有可信 `notifyId` 做主键，
   强写会产生无主记录。这是任务单原有的口径，实现照办。

2. **引入 `node-red-contrib-postgresql` 0.16.2。** Node-RED 4.0.5 官方镜像不带任何
   数据库节点，也没有 `psql`，而 `notify_log` 必须由本层写。镜像里装包，版本锁补丁号，
   与 `deploy/versions.env` 的口径一致。这是新增第三方依赖，已同步 `AGENTS.md` 的依赖清单。

3. **Node-RED 只有一个 HTTP 端口 1880。** 概要设计 §4.2 的端口表写 `1880·1881`，
   但 4.0.5 已移除 `httpNodePort`，编辑器与 `/api/notify` 共用一个监听口。
   `.env.example` 的 `NOTIFY_ENDPOINT` 改为 `http://localhost:1880/api/notify`，
   文档偏差见 O-17。

4. **`workshop_notify` 增加 `alarm` 只读权限。** 接口规范 §11.5 的卡片带 `alarm.alarmId`，
   `notify_log.alarm_id` 是它的外键，而 001 的授权矩阵只给了 `notify_log` 读写 + 配置域只读。
   只加 `SELECT`，不给写——通知失败不回滚告警，编排层不该有改告警状态的能力。
   `03_grant.sql`、`docs/03` §6 与 `.claude/rules/deploy-config.md` 已同步。

5. **`alarm_id` 回查不到时留空。** `adapter` 先落库再发通知，理论上一定查得到；
   查不到说明告警已被清理，此时卡片照发，只是少一个交叉索引，不阻塞投递。

6. **level 2 按立即通知处理。** 与 010 同一个口径，5 分钟合并没有落点（O-09），
   不在 adapter 与 Node-RED 各写一版。

7. **`deploy/node-red` 整目录挂到容器 `/data`。** 先试过只挂两个文件，
   编辑器「部署」报 `EBUSY: rename flows.json`——单文件挂载是挂载点，不能原子替换。
   整目录挂载后编辑器能正常写回，运行时产物（`.config.*`、`package.json`、
   `flows_cred.json`、`node_modules/`）已进 `.gitignore`。
   因此「编辑器里改完必须导出提交」仍靠流程约束，不再由挂载只读强制。

8. **`credentialSecret: false`。** 流程里没有任何 Node-RED 凭据（数据库口令走环境变量），
   不关掉加密会在每次启动生成随机密钥并刷一段警告，还会在 `deploy/node-red` 留一个
   `flows_cred.json`。

9. **投递单次超时 5 秒。** `http request` 默认 120 秒，通道挂死时一次重试就能把
   「1 / 5 / 15 秒」的阶梯拖成 8 分钟。写入 `msg.requestTimeout`。

10. **写投递日志失败重试 3 次（1 秒间隔）。** 详细设计 §4.4 的「数据库写失败重试 3 次」
    在本层落点。响应早已发出，重试不拖慢调用方；3 次仍失败记 `node.error` 并终止，
    不无限重试。

11. **`flows.json` 由生成脚本产出后再经编辑器导出核对。** 本次用临时 Node-RED
    实例 `POST /flows` 让 4.0.5 自己写一遍，导出结果与提交内容逐字段一致
    （21 个节点、无字段差异），所以文件确实是编辑器可识别的形态。
