# 010 告警判定段

> 计划任务：M9（复杂度 L）　状态：已完成

## 要建什么

消费有界队列，做阈值求值、去抖、告警状态机、通知请求、活动集合重建。单消费者单写者，不加锁。

## 验收

- [x] 模拟量连续 N 次越限才告警，单次波动不告警，N 按测点配置（`BR-32`）
- [x] 恢复需**连续 N 次**不满足（不是首次未命中），与触发对称（`BR-33`）— 见「偏差」
- [x] 开关量当次即告警、当次即恢复，不去抖（`BR-34`）
- [x] 高高限触发时闭合同测点的高限活动告警
- [x] 质量非 `GOOD` 不参与求值，在入口即返回（`BR-18`）
- [x] 补传数据只记告警、不发通知（`BR-36`）
- [x] 同测点同规则未恢复期间不重复拉响（`BR-38`）
- [x] 判定与排序一律用 `collectTime`，不用 `receiveTime`（`BR-35`）
- [x] 重启后活动告警集合从库重建，不重复拉响
- [x] 阈值改后 60 秒内生效，整表原子替换不逐条更新
- [x] 通知异步发出，adapter 内无重试；按级别决定是否通知（`BR-39`）
- [x] 队列满时丢弃并计数，不阻塞入库
- [x] 状态四态：`ACTIVE` / `RECOVERED` / `ACKED` / `CLOSED`（`BR-31`）

## 偏差

1. **恢复条件与详细设计冲突**：A9 伪码写 `if !hit && n == 0`（首次未命中即恢复），与
   BR-33「连续 N 次」矛盾。按 BR-33 实现，与触发对称。已登记为 O-08，
   见 `../docs/07-待确认项与开放决策.md`。

2. **level=2 的 5 分钟合并未落点**（O-09，见 `../docs/07-待确认项与开放决策.md`），
   本期按立即通知实现，不与其他组件各写一版。

3. **去抖计数用 `>=` 而非 `==`。** 判据写成 `n == N` 时，落库失败会让计数停在第 N 次，
   后续命中永远满足「大于 N」而不再重试，一次瞬时的写库失败就能让这条告警再也拉不响，
   直到数值回落把计数清零。改用 `>=` 后每次命中都会重试，且不会重复拉响——
   拉响后键已进活动集合，条件里的 `!active.Has(key)` 挡住后续。回归测试
   `TestRaiseRetriesAfterWriteFailure`。

4. **迟到的旧读数不参与判定。** 判定段为每个测点记最近一次已判定的 `collectTime`，
   更早的读数直接丢弃。若参与判定，它会倒退去抖计数，让告警在抖动中反复拉响与恢复。
   补传行不受此限：它的时间轴本来就是过去，参与比较会被全部拒掉，而补传告警要落库。
   回归测试 `TestStaleReadingIsIgnored`。

5. **同一次求值内规则按级别从高到低处理。** 否则「温度从 80 跳到 110」这一批读数会先拉响
   高限、随即被高高限闭合，白产生一条告警与一次通知。级别高的先处理时，
   低级别规则被 `active.HighestLevelOnPoint` 挡住，直接不产生。

6. **接收段投递前先过滤 `status == OK`。** `Result.Rows` 在重复消息上仍带解码结果
   （`Handle` 只把 `Status` 改成 `DUPLICATE`），原样投递会让同一批读数被数两次，
   去抖计数提前达标造成误报。落点在 `cmd/proto-adapter/evaluate.go` 的 `dispatch`。

7. **坏点在投递端就丢掉，不进判定队列。** `Queue.Push` 拦掉 `quality != GOOD` 的读数：
   它在判定入口必被丢弃，占着队列只会把可用读数挤掉，让告警更容易漏。

8. **通知关闭时不建投递器。** `NOTIFY_ENABLED=false` 或 `NOTIFY_ENDPOINT` 为空时
   `evaluateDeps.notify` 为 nil，判定段完全不投递。若改成一个「空转成功」的投递器，
   「跳过」会被统计成「已发送」，健康检查看到的是假成功数。

9. **活动告警数不与库比对。** `.claude/rules/adapter-evaluate.md` 的健康判据要求
   「活动告警数 ≠ DB 未恢复告警数」时报告异常，该判据落在 015（`/healthz`），
   本任务只提供 `Evaluator.Stats()` 与 `Queue` 的深度/容量/丢弃数。

10. **文件拆分为 `active.go` / `counters.go` 两份。** 详细设计 §1.1 的目录树就是这样分的。
    两者都在 `internal/adapter/state`，单写者、无锁。

11. **`notify_log` 不在本任务写。** 投递日志由编排层（011 的 N-02）在投递后写；
    adapter 只发请求不记结果，记了也会与编排层的记录重复。
